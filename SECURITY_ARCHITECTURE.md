# VaultPass Desktop - Security Architecture Manifesto

This document formalizes the architectural defense mechanisms implemented in VaultPass Desktop. It serves as a permanent reference for future development to ensure the offline-first, local-only, and zero-knowledge paradigms are never compromised.

## 1. Domain Dominance

The core philosophy of VaultPass is that **the Domain Layer dictates security, not the UI.**
*   **Session State Supremacy**: The UI does not manage whether the app is locked or unlocked. The domain `SessionManager` tracks states (`LOCKED`, `UNLOCKING`, `BACKGROUND`). If the OS minimizes the app, the domain unilaterally transitions to `BACKGROUND` and wipes keys, forcing the UI to adapt without any explicit UI logic.
*   **Reactive Flow Data**: Data flows upward from the local database via Kotlin `Flow`s. If a background sync job modifies the database, the Repositories automatically emit the new state to the ViewModels. The UI is completely agnostic to how data arrived on the disk.

## 2. Secure Memory Management

Standard Kotlin/Java `String` objects are immutable and pooled, meaning sensitive data can linger in the heap indefinitely and be extracted via memory dumps.
*   **Type-Safe Wrapping**: VaultPass uses `SecureCharArray` and raw `ByteArray` structures for Master Passwords, DEKs (Data Encryption Keys), and unencrypted secrets.
*   **Explicit Wiping**: Because these structures wrap primitive arrays, they expose explicit `.wipe()` methods. When the `SessionManager` transitions to `CLOSING` or `LOCKED`, it loops through active structures and overwrites them with zeros (`\u0000`).
*   **Time-Limited Clipboard**: Passwords copied to the clipboard use the `SecureClipboardManager`, which automatically scrubs the OS clipboard buffer after a predetermined TTL (e.g., 30 seconds).

## 3. Cryptographic and Format Agility

VaultPass never hardcodes cryptographic parameters, ensuring future-proofing against algorithmic obsolescence.
*   **Vault Format Versioning**: Every vault tracks its structural version. Future versions of VaultPass will use the `MigrationRunner` to safely upgrade old SQLite schemas.
*   **Dynamic KDF Metadata**: The KDF algorithm, iteration count and salt length are stored alongside the vault, so they can change in a later version without breaking existing vaults. New vaults use PBKDF2-HMAC-SHA256 with 300,000 iterations.
*   **Cipher Versioning**: The application supports migrating from AES-256-GCM to future ciphers (like XChaCha20-Poly1305) by reading the vault's embedded `EncryptionConfig`.

## 4. Centralized Error Handling

VaultPass prevents cryptographic or database crashes from ever leaking untyped, raw exceptions to the presentation layer.
*   **VaultError Hierarchy**: All exceptions (e.g., `SQLiteException`, `IOException`) are caught in the Repository layer and mapped to typed domain errors like `DatabaseError.DiskFull` or `AuthError.IncorrectPassword`.
*   **Result Pattern**: The `RepositoryResult` enforces this mapping at compile-time, guaranteeing that the Compose UI can exhaustively match on known error states to display localized warnings instead of cryptic stack traces.

## 5. Secure Logging

*   **Type-Safe Redaction**: `SecureCharArray` and domain models (like `VaultEntry`) explicitly override `toString()` to return redacted placeholders (`[REDACTED]`).
*   **Sanitization Middleware**: All logging is routed through `VaultLogger`, which utilizes a `LogSanitizer` to heuristically strip keys, passwords, and JWTs before they are written to disk. Debugging remains safe.

## 6. OS & Platform Abstraction

To ensure VaultPass can trivially port to macOS or Linux, all native interactions are strictly decoupled.
*   **Platform Boundaries**: Interfaces like `SystemTrayProvider`, `NotificationProvider`, `BiometricAuthenticator`, and `FilePicker` define the required capabilities. The domain never imports Windows APIs. Support for a new OS is achieved merely by swapping out the data layer implementation.

## 7. Feature Isolation (Toggles)

*   **FeatureManager**: `FeatureManager` and the `FeatureFlag` registry exist, but no feature is gated by them yet. LAN sync is always available; it only uses the network while the Sync page is open.

## 8. LAN Sync with VaultPass for Android

*   **Shared, verified core**: The sync crypto, handshake, framing, discovery beacons and merge plans live in `com.vaultpass.synccore`, which is byte-identical in the Android and desktop apps.
*   **Authenticated encryption only**: Every connection starts with a P-256 key exchange authenticated by a pairing key; every message after it is encrypted with AES-256-GCM and numbered, so replayed or altered messages end the connection. Pairing keys are stored sealed with the vault key.
*   **Confirmed result**: A sync reports success only when both devices send the same vault fingerprint. A failed sync shows the user its reason.
*   The full protocol is in [SYNC_PROTOCOL.md](SYNC_PROTOCOL.md).

## 9. Signed Updates

*   **What is signed**: Each release installer `VaultPass-Setup-vX.Y.Z.exe` is published with `VaultPass-Setup-vX.Y.Z.exe.sig`: one line of base64 holding a DER ECDSA P-256 signature (`SHA256withECDSA`) over the UTF-8 text `VaultPass-Desktop-Update-v1`, the installer's file name and the lower-case hex SHA-256 of its bytes, one per line (newline-separated, no trailing newline). A `.sha256` file is published for people who want to check the download by hand; the app does not rely on it.
*   **Trust anchor**: The app carries the release public key in `src/main/resources/update-signing-key.pem` (PEM `PUBLIC KEY`). Only EC P-256 keys are accepted. If the file is missing or invalid, the updater refuses every update and says "Updates are disabled: this build has no update signing key". The private key lives in a password-protected PKCS12 file outside the repository. This is the project's own key, not a Windows Authenticode certificate, so Windows SmartScreen still treats the installer as unsigned.
*   **Signing**: Releases are signed by `tools/SignInstaller.java`, a standalone JDK program run by `build-installer.ps1`, so the private key is decrypted only in that process (password from a hidden console prompt, never an environment variable). It signs only `major.minor.patch` versions, only a file named `VaultPass-Setup-v<version>.exe`, and only when the built app image contains the same public key as the repository, then checks the new signature with the app's own `UpdateSignatureVerifier` from that image.
*   **Versions**: The updater treats a release as an update only if its tag is `major.minor.patch` (optionally with a leading `v`) in ASCII digits and numerically greater than the running version. Pre-release and any other tags are never offered.
*   **Check before install**: The updater picks only the asset named exactly `VaultPass-Setup-v<version>.exe` (there is no fallback to another `.exe`) and requires its `.sig` asset; a release without one is refused as unsigned. It downloads both over https only (a redirect to http is refused), caps the installer at 500 MB, checks the SHA-256 digest GitHub reports for the asset when there is one, and verifies the signature with the embedded key against the message rebuilt from the file name the release tag implies (`VaultPass-Setup-v<tag version>.exe`) and the hash of the downloaded bytes. Because the version is part of what is signed, an older signed installer republished or renamed under a newer tag fails the check, which blocks downgrades through a compromised release. Any failure deletes the download and shows the reason.
*   **Download folder**: Downloads go to the `updates` folder inside the data folder (`<install folder>\data\updates` for an installed copy), not to `%TEMP%`. The installer is written as `VaultPass-Setup-vX.Y.Z.exe.part` and renamed to its real name only after the signature verified, so a file with the installer's name is always one that passed the check. A cancelled or failed download deletes the `.part` file. At startup and before each download, the updater deletes old installers, `.part` files and Setup logs older than 30 days in that folder; it deletes only regular files with exactly those names, never links, folders or other files. The folder is protected only as well as the data folder is (see section 10), so the protection still comes from the signature check and the locked handle below, not from the folder.
*   **Check again at launch**: Right before running the installer, the updater opens it with a Windows handle that denies other processes write and delete access, re-hashes it and verifies the signature through that handle, and keeps the handle open until Windows has started the installer. It refuses to run a file that changed since the download, or a file the updater did not download and check itself. The check, the steps before exit and the launch all run on one thread. This narrows the window in which another process could swap the file after it was checked; it does not eliminate it, because the file sits in the updates folder between the download and the launch. Once started, Inno Setup's own loader still unpacks its setup program, and the folder permission script, to a new folder under the user's `%TEMP%`; that is how every Inno Setup installer runs.
*   **Before exit**: After the locked re-check passes and before the installer starts, VaultPass stops sync networking, clears a password it copied to the clipboard, locks the vault (wiping the keys) and closes the database. A failure in these steps is logged and doesn't stop the update. If the installer then can't be started, VaultPass says so and stays locked until the user unlocks it.
*   **Install on close**: "Later" marks the update to be installed when VaultPass closes. The mark is cleared as soon as the update is no longer ready to install. On close, the installer is started only if Windows isn't shutting down or signing out, and never from a JVM shutdown hook. If Windows shuts down or signs out instead, the update isn't installed, and the next start says so.
*   **Installed copies only**: The updater installs an update only when the install folder registered by Setup (the `Inno Setup: App Path` value of VaultPass's uninstall entry) is the folder this copy runs from. Any other copy, such as one unpacked or copied by hand, is refused with "This copy of VaultPass wasn't installed by its Setup program, so it can't update itself. Download the installer from GitHub instead."
*   **Command line and relaunch**: The installer is started with `/SILENT /NORESTART`, a log file in the updates folder and `/DIR` set to the folder this copy runs from. "Restart now" adds `/RELAUNCH=1`, and the installer starts VaultPass again when it has finished. If the update fails before Setup has copied its files, Setup starts the version still installed with `--update-not-installed`, and it shows that the update didn't install. If it fails after the old program files were removed, so `VaultPass.exe`, `app\VaultPass.cfg` or the Java runtime is missing, Setup starts itself again (`{srcexe}`) with the same `/DIR`, interactive and without `/SILENT` or `/RELAUNCH`, so the user can finish the installation and the restart can't repeat itself. Before the launch the updater writes `pending-update.json` in the updates folder; if the next start still runs an older version than the one named there, the user is told that the update didn't install.
*   **Assumption about the installed app**: The check runs inside the installed VaultPass, so it is only as trustworthy as the installed program files: they must not be modifiable by other users or by unprivileged programs. The installer limits the install folder to the user's account (section 10). Where it can't, the app shows a warning.
*   **Limits**: A stolen private key and password, or a malicious build signed by the maintainer, would still be installed. Losing the key means installed apps can't accept updates until users install a build with a new key by hand. Release steps are in [RELEASING.md](RELEASING.md).

## 10. Install Folder Permissions

*   **Default folder**: New installs go to `%LOCALAPPDATA%\Programs\VaultPass`. An existing install keeps its folder, including the old default `C:\VaultPass`. The installer refuses the root of a drive. It accepts a folder that isn't empty only when it holds `VaultPass.exe`, is the folder of the registered install (`Inno Setup: App Path`, compared without case and trailing backslash), or holds nothing but a `data` folder with a vault in it.
*   **Owner-only folder**: On every install and update, the installer runs `installer\restrict-folder.ps1` as the user who started Setup. It refuses a folder that is itself a junction or symbolic link. It replaces the install folder's permissions with Full control for that account, SYSTEM and Administrators only, with nothing inherited from the parent folder. Then, one folder at a time, it resets everything inside (the program files and the `data` folder with the vault) to inherit only those entries (`icacls /reset /C /L`) and makes that account the owner of every item (`icacls /setowner /C /L`), so items another account created there become the user's. `/L` changes a junction or symbolic link itself; the script never enters one, so nothing outside the install folder is changed (`icacls /T` is not used because it walks into junctions even with `/L`). Finally it reads back the folder, its `data` folder and every item inside, without following links, and checks that no account other than those three is listed and that every owner is the user, SYSTEM or Administrators. Other Windows accounts on the same PC can then neither change the program nor read the vault.
*   **Planted files**: Before copying its files, and only in a folder that holds `VaultPass.exe` or is the registered install folder, the installer deletes these files directly in the install folder: `*.dll`, `*.manifest`, `*.cfg`, `*.local`, and `*.exe` except `VaultPass.exe` and the uninstaller `unins000.exe`. It also deletes `*.local` folders (DLL redirection) and replaces the `app` and `runtime` folders. Other files directly in the install folder, such as the uninstaller's log `unins000.dat`, and the files inside `data` are not deleted; for those, and for everything else inside the install folder, the protection is the permission and owner reset above. Updates skip the folder page, so these deletions check the folder themselves rather than relying on the page's checks.
*   **When the permissions can't be applied**: On drives without Windows permissions (FAT32, exFAT), or when the script fails, the folder keeps the permissions it had. The script also reports items it couldn't reset or give to the user, items that still list another account or owner, and links inside the folder; a `data` folder that is a link counts as a failure, because the vault it points to was not changed. The installer logs the reason, an interactive install shows a warning naming the folder, and the installation continues. The reason is written to `data\folder-permissions-not-restricted.txt`; while that file exists, VaultPass shows a warning with that reason after unlock. A later install that succeeds deletes the file.
*   **Scope**: Only the install folder is changed. A data folder outside it (`~/.vaultpass`, or one set with `-Dvaultpass.data.dir`) keeps its own permissions; the user profile is already private to its account.
